# Задание 7

## Коллекция orders
### Основные операции:

1. Быстрое создание заказов с одновременным списанием остатков (создание заказа идет в рамках конкретного ид пользователя);
2. Поиск истории заказов конкретного пользователя (поиск идет по ид пользователя);
3. Отображение статуса заказа (по ид заказа, но если статус запрашивает пользователь, а не администратор, то тоже знаем его ид);

### Выбор стратегии шардирования
Так как основным атрибутом в частых операциях является ид пользователя, то предлагается сделать его шард-ключом.

**Стратегия:** hashed по customer_id.

Плюсы: Targeted-операция для истории заказов пользователя; равномерное распределение; все заказы клиента на одном шарде;

Минусы: Статус по order_id без customer_id broadcast-операция;

```shell
sh.shardCollection("shop.orders", { customer_id: "hashed" })
```

**Индексы**
В основных операциях используется поиск по ид заказа, _id уже проиндексирован по умолчанию на каждом шарде.

**Схема:** 
```shell
{
  _id: ObjectId,                 // order_id
  customer_id: ObjectId,
  created_at: ISODate(...),
  items: [
    {
      product_id: ObjectId,
      name: "Смартфон X",
      quantity: 1,
      price_at_purchase: NumberDecimal("49990.00"),
      geozone: "Moscow"
    }
  ],
  status: "created",             // created | paid | shipped | delivered | cancelled
  total: NumberDecimal("49990.00"),
  geozone: "Moscow"
}
```

## Коллекция products

### Основные операции:

1. Частые обновления остатков при покупках (поиск товара по ид);
2. Поиск товаров по категориям и фильтрация по диапазону цен (поиск товаров по категории и цене);
3. Описание товара на странице продукта (поиск товара по ид);

### Выбор стратегии шардирования
Так как основным атрибутом в частых операциях является ид товара, то предлагается сделать его шард-ключом.

**Стратегия:** hashed по product_id.

Плюсы: Targeted-операция для страницы товара и частых обновлений остатков; равномерное распределение;

Минусы: Поиск по category/price становятся broadcast-операциями;

```shell
sh.shardCollection("shop.products", { _id: "hashed" })
```

**Индексы**
Для увеличения скорости поиска по категории и цене предлагается так же создать индекс:
```shell
db.products.createIndex({ category: 1, price: 1 })
```
**Схема:** 
```shell
{
  _id: ObjectId,                 // product_id
  sku: "SM-X-128-BLK",
  name: "Смартфон X",
  category: "electronics",
  price: NumberDecimal("49990.00"),
  stock: {                       // остатки по геозонам
    "Moscow":        { qty: 50 },
    "Ekaterinburg":  { qty: 50 },
    "Kaliningrad":   { qty: 30 }
  },
  attributes: {
    color: "black",
    size: "128GB"
  },
  created_at: ISODate(...),
  updated_at: ISODate(...)
}
```

## Коллекция carts

### Основные операции:

1. Создание корзины, когда заходит гость или новый пользователь. Получение текущей корзины по фильтру { session_id, status:"active" } или { user_id, status:"active" };
2. Добавление или замена товара в корзине;
3. Удаление товара из корзины;
4. Слияние гостевой корзины в пользовательскую, если пользователь залогинится: 
   4.1. прочитать гостевую { session_id, status:"active" };
   4.2. добавить её items в корзину { user_id, status:"active" };
   4.3. отметить гостевую как abandoned;
5. Отметка корзины как заказанной;

### Выбор стратегии шардирования
Так как текущая корзина получается по session_id/user_id, а все остальные действия связаны с текущей корзиной (то есть в контексте запросов всегда есть session_id/user_id), то предлагается сделать session_id/user_id шард-ключом. Для единообразия шардирования вводим новый атрибут owner_key, где будет отображаться значение session_id/user_id.

**Стратегия:** hashed по owner_key.

Плюсы: Targeted-операция для user_id и session_id через единый ключ; равномерное распределение;	

Минусы: Нужно добавить фиктивное поле owner_key; Поиск по id_cart становится broadcast-операцией, если в запросе не указан owner_key;

```shell
sh.shardCollection("shop.carts", { owner_key: "hashed" })
```

**Индексы**
Для увеличения скорости поиска по статусу и времени удаления предлагается так же создать индексы:
```shell
db.carts.createIndex({ owner_key: 1, status: 1 })
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })
```
**Схема:** 
```shell
{
  _id: ObjectId,                 // cart_id
  owner_key: "user:12345",       // фиктивный ключ для шардирования
  user_id: ObjectId | null,
  session_id: "sess_abc" | null,
  items: [
    {
      product_id: ObjectId,
      quantity: 2,
      added_at: ISODate(...)
    }
  ],
  status: "active",              // active | ordered | abandoned
  created_at: ISODate(...),
  updated_at: ISODate(...),
  expires_at: ISODate(...)       // TTL
}
```

## Метрики для мониторинга состояния шардов
Сбор метрик можно организовать через mongodb_exporter для Prometheus, где можно настроить дашборды.

|**Уровень**|**Метрика/Команда**|**Описание**|
| :- | :- | :- |
|Кластер  | sh.status()	                                    | Показывает распределение чанков по шардам. Позволяет найти шарды с аномально большим или малым числом чанков |
|Кластер  | sh.getBalancerState() / sh.isBalancerRunning()  | Состояние балансировщика. Если он выключен или не работает, данные не будут перераспределяться               |
|Кластер  | config.chunks                                   | Точное количество чанков на шард. Позволяет быстро найти перегруженные узлы                                  |
|Шард     | db.serverStatus().opLatencies	                | Задержка операций. На «горячем» шарде она будет значительно выше, чем на остальных                           |
|Шард     | db.currentOp({ "secs_running": { "$gt": 10 } }) | Длительные операции. Могут указывать на узкие места в производительности шарда                               |
|Данные   | db.collection.getShardDistribution()            | Распределение данных конкретной коллекции по шардам. Помогает увидеть, как категория «Электроника»           |
|         |                                                 | распределяется по кластеру                                                                                   |
|Данные	  |	config.chunks.find({ jumbo: true })	            | «Джамбо-чанки». Это чанки, которые не могут быть разделены из-за низкой кардинальности ключа. Они блокируют  |
|         |                                                 | миграцию и могут быть причиной постоянной перегрузки                                                         |

## Механизмы автоматического перераспределения данных
1. Настройка балансировщика (окно активности, размер чанка);
2. Зонное шардирование (можно привязать диапазон ключей, соответствующий категории «Электроника», к выделенной группе шардов с более производительным железом);
3. Пересмотр шард-ключа;
4. Добавление новых шардов.
