# Задание 7

## Коллекция orders
### Основные операции:

1. Быстрое создание заказов с одновременным списанием остатков (создание заказа идет в рамках конкретного ид пользователя);
2. Поиск истории заказов конкретного пользователя (поиск идет по ид пользователя);
3. Отображение статуса заказа (по ид заказа, но если статус запрашивает пользователь, а не администратор, то тоже знаем его ид);

### Выбор стратегии шардирования
Так как основным атрибутом в частых операциях является ид пользователя, то предлагается сделать его шард-ключом.

**Стратегия:** hashed по customer_id.

Плюсы: Targeted-операция для истории заказов пользователя; равномерное распределение; все заказы клиента на одном шарде;

Минусы: Статус по order_id без customer_id broadcast-операция;

```shell
sh.shardCollection("shop.orders", { customer_id: "hashed" })
```

**Индексы**
В основных операциях используется поиск по ид заказа, _id уже проиндексирован по умолчанию на каждом шарде.
```shell
db.orders.createIndex({ customer_id: 1, created_at: -1 })
```

**Схема:** 
```shell
{
  _id: ObjectId,                 // order_id
  customer_id: ObjectId,
  created_at: ISODate(...),
  items: [
    {
      product_id: ObjectId,
      name: "Смартфон X",
      quantity: 1,
      price_at_purchase: NumberDecimal("49990.00"),
      geozone: "Moscow"
    }
  ],
  status: "created",             // created | paid | shipped | delivered | cancelled
  total: NumberDecimal("49990.00"),
  geozone: "Moscow"
}
```

## Коллекция products

### Основные операции:

1. Частые обновления остатков при покупках (поиск товара по ид);
2. Поиск товаров по категориям и фильтрация по диапазону цен (поиск товаров по категории и цене);
3. Описание товара на странице продукта (поиск товара по ид);

### Выбор стратегии шардирования
Так как основным атрибутом в частых операциях является ид товара, то предлагается сделать его шард-ключом.

**Стратегия:** hashed по product_id.

Плюсы: Targeted-операция для страницы товара и частых обновлений остатков; равномерное распределение;

Минусы: Поиск по category/price становятся broadcast-операциями;

```shell
sh.shardCollection("shop.products", { _id: "hashed" })
```

**Индексы**
Для увеличения скорости поиска по категории и цене предлагается так же создать индекс:
```shell
db.products.createIndex({ category: 1, price: 1 })
```
**Схема:** 
```shell
{
  _id: ObjectId,                 // product_id
  sku: "SM-X-128-BLK",
  name: "Смартфон X",
  category: "electronics",
  price: NumberDecimal("49990.00"),
  stock: {                       // остатки по геозонам
    "Moscow":        { qty: 50 },
    "Ekaterinburg":  { qty: 50 },
    "Kaliningrad":   { qty: 30 }
  },
  attributes: {
    color: "black",
    size: "128GB"
  },
  created_at: ISODate(...),
  updated_at: ISODate(...)
}
```

## Коллекция carts

### Основные операции:

1. Создание корзины, когда заходит гость или новый пользователь. Получение текущей корзины по фильтру { session_id, status:"active" } или { user_id, status:"active" };
2. Добавление или замена товара в корзине;
3. Удаление товара из корзины;
4. Слияние гостевой корзины в пользовательскую, если пользователь залогинится: 
   4.1. прочитать гостевую { session_id, status:"active" };
   4.2. добавить её items в корзину { user_id, status:"active" };
   4.3. отметить гостевую как abandoned;
5. Отметка корзины как заказанной;

### Выбор стратегии шардирования
Так как текущая корзина получается по session_id/user_id, а все остальные действия связаны с текущей корзиной (то есть в контексте запросов всегда есть session_id/user_id), то предлагается сделать session_id/user_id шард-ключом. Для единообразия шардирования вводим новый атрибут owner_key, где будет отображаться значение session_id/user_id.

**Стратегия:** hashed по owner_key.

Плюсы: Targeted-операция для user_id и session_id через единый ключ; равномерное распределение;	

Минусы: Нужно добавить фиктивное поле owner_key; Поиск по id_cart становится broadcast-операцией, если в запросе не указан owner_key;

```shell
sh.shardCollection("shop.carts", { owner_key: "hashed" })
```

**Индексы**
Для увеличения скорости поиска по статусу и времени удаления предлагается так же создать индексы:
```shell
db.carts.createIndex({ owner_key: 1, status: 1 })
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })
```
**Схема:** 
```shell
{
  _id: ObjectId,                 // cart_id
  owner_key: "user:12345",       // фиктивный ключ для шардирования
  user_id: ObjectId | null,
  session_id: "sess_abc" | null,
  items: [
    {
      product_id: ObjectId,
      quantity: 2,
      added_at: ISODate(...)
    }
  ],
  status: "active",              // active | ordered | abandoned
  created_at: ISODate(...),
  updated_at: ISODate(...),
  expires_at: ISODate(...)       // TTL
}
```

# Задание 10
## Критичность данных и обоснование применения Cassandra

Критичны с точки зрения целостности (нельзя потерять или исказить, нужна атомарность и строгая согласованность):
1. Заказы - финансовые обязательства перед клиентом. Потеря или частичная запись заказа наносит прямой ущерб и репутационные потери;
2. Остатки товаров - возможна продажа недоступного товара;
3. Корзина - добавление/удаление товара должно быть атомарным. При логине должно происходить полное слияние гостевой в пользовательскую;
4. История заказов - аудит и юридическая значимость. Каждое событие должно быть зафиксировано и не потеряно.

Критичны с точки зрения скорости обработки:
1. История заказов пользователя - читается при каждом заходе в личный кабинет, должна отдаваться быстро даже при миллионах заказов;
2. Статусы заказов - опрашиваются часто, должны читаться точечно по ключу;
3. Карточка товара - массовые чтения при просмотре каталога. Скорость обработки операции напрямую влияет на продажи;
4. Список товаров - массовые чтения при просмотре каталога и поиску нужного товара. Скорость обработки операции напрямую влияет на продажи.

Применение Cassandra в «Мобильном мире» имеет смысл для append-only и time-series данных: заказов, истории статусов (если нужно хранить историю, либо обновлять как парамтер заказа) и пользовательских сессий. Эти сущности выигрывают от линейного горизонтального масштабирования, геораспределённой репликации без полного перераспределения данных и высокой пропускной способности записи, а их требования к целостности закрываются настройкой Hinted Handoff/Read Repair/Anti-Entropy Repair.

Для корзин и товаров Cassandra не подходит: операции с ними требуют read-modify-write, условных обновлений и кросс-партиционной фильтрации, которых в Cassandra либо нет, либо они реализуются дорогими обходными путями. Эти сущности остаются в MongoDB.

## Концептуальная модель для Cassandra

Можно выделить три ключевых правила для моделирования:
1. Одна таблица - один запрос. Если у сущности несколько точек входа (например, для таблицы заказов пиоск по customer_id, по order_id), то получается несколько таблиц-проекций;
2. Partition key - высокая кардинальность, равномерный хэш, отсутствие монотонности. UUID, а не timestamp/auto-increment. Статус, категрия, геозона в partition key - это низкая кардинальность и гарантированные горячие партиции;
3. Bounded partitions - гарантирует, что размер каждой логической группы данных не будет расти бесконечно. Для time-series - обязательный временной бакет, иначе партиция растёт неограниченно и превращается в узкое место.

### orders_by_customer - история заказов пользователя
```sql
CREATE TYPE order_item (
    product_id      uuid,
    name            text,
    quantity        int,
    price_at_purchase decimal,
    geozone         text
);

CREATE TABLE orders_by_customer (
    customer_id   uuid,
    order_date    timestamp,
    order_id      uuid,
    status        text,
    total         decimal,
    geozone       text,
    items         list<frozen<order_item>>,
    PRIMARY KEY ((customer_id), order_date, order_id)
) WITH CLUSTERING ORDER BY (order_date DESC, order_id ASC);
```

**Partition key: customer_id**
1. Высокая кардинальность: миллионы UUID, хэш равномерно распределяет их по токен-кольцу значит каждый узел получает примерно одинаковую долю заказов;
2. UUID не монотонен, все узлы пишутся равномерно;
3. Все заказы одного клиента лежат в одной партиции на одном узле;
4. Clustering order_date DESC, order_id: Cassandra хранит строки в партиции уже в этом порядке;

Горячие партиции: риск только у клиента с десятками тысяч заказов (бот или корпоративный клиент). 

### orders_by_id - точечный поиск по номеру заказа
```sql
CREATE TABLE orders_by_id (
    order_id      uuid PRIMARY KEY,
    customer_id   uuid,
    order_date    timestamp,
    status        text,
    total         decimal,
    geozone       text,
    items         list<frozen<order_item>>
);
```
**Partition key: order_id**

1. Высокая кардинальность;
2. Одна строка на партицию;
3. Запрос статуса по номеру заказа (админ) дает точечное чтение;

Горячие партиции: невозможны - каждая партиция содержит ровно один заказ.

Это осознанная денормализация: при создании заказа приложение пишет и в orders_by_customer, и в orders_by_id, чтобы избежать полного сканирования всех узлов кластера

### sessions - состояние сессии
```sql
CREATE TABLE sessions (
    session_id    text PRIMARY KEY,
    user_id       uuid,
    created_at    timestamp,
    last_seen_at  timestamp,
    data          map<text, text>
) WITH default_time_to_live = 86400;
```
**Partition key: session_id**
1. Высокая кардинальность;
2. Одна строка на партицию;
3. TTL 24 часа удаляет сессии автоматически, без DELETE - нет tombstones.
4. Если поле last_seen_at обновляется на каждый HTTP-запрос - одна строка перезаписывается тысячи раз в секунду, что может привести к снижению производительности. Нужно обновлять last_seen_at не чаще раза в 1–5 минут.


При стандартном подходе hash-based sharding (MongoDB) (когда мы добавляем или удаляем сервер в распределённой базе данных) приходится перераспределять данные между узлами. В результате простое решение (например, хеш ключа по модулю числа серверов) приводит к следующей проблеме. Если число серверов меняется, то почти все ключи «переезжают» на новые узлы. Из-за этого клиенты обращаются за данными не туда, что провоцирует массовые cache miss’ы, перегрузку базы и падение производительности системы. Consistent hashing (Cassandra) решает эту проблему, потому что при изменении числа узлов перераспределяется лишь небольшая часть данных, а остальные остаются на своих местах.  

## Выбор стратегии для обеспечения целостности данных

**Заказы (orders_by_customer, orders_by_id)**	
1. Стратегрия: Hinted Handoff (основной) + Anti-Entropy Repair (страховка) + Read Repair (на чтении);
2. Условие согласованности: строгий кворум W + R > N или локальный кворум в случае геораспределенности дата центров;
3. Обоснование: заказы - критичные финансовые данные. Кворум на запись гарантирует, что большинство реплик подтвердили заказ до ответа клиенту. Hinted Handoff закрывает короткие отказы (до 3 часов). Read Repair при чтении исправляет расхождения на горячих ключах. Anti-Entropy Repair — обязательная страховка для «холодных» заказов, которые никто не читает: без него расхождения на них останутся навсегда, но запускается только в окно низкой нагрузки. Кворум даёт сильную согласованность, что необходимо для финансовых данных. 
   
**Сессии (sessions)**	
1. Стратегия: Hinted Handoff;
2. Условие согласованности: W=1, R=1;	
3. Обоснование: потеря сессии при отказе узла означает лишь повторный логин, а не финансовый ущерб. Условия согласованности минимизируют задержку. Anti-Entropy Repair для сессий избыточен из-за TTL (24 часа). Read Repair тоже избыточен так как координатор читает только одну реплику.
